Interface & Frontend Layer

Deep dive into the Angular components orchestrating user input, state transitions, and zero-latency polling.

Overview

The frontend layer is composed of two primary Angular components located in the manager-frontend package:

  • Run Transaction Component (run-transaction.ts): Acts as the workflow launcher and initiator.
  • Workflow Task Component (workflow-task.ts): Handles rendering form inputs dynamically, saving intermediate states, and managing transitions between sequence steps.

1. Initiating the Sequence

The flow begins in run-transaction.ts. Here, the user selects the target transaction event and the transactionsequence workflow.

Session Initialization & Cleanup

Before starting the workflow, startWorkflow() prepares the session object: 

// Always update these fields for the new transaction run.
sessionData['dataset:transaction'] = this.transactionEvent;
sessionData['dataset:sessionworkflow'] = this.selectedWorkflow;
if (this.selectedWorkflow === 'transactionsequence') {
  sessionData['dataset:uniquegenericname'] = this.uniqueGenericName;
  sessionData['dataset:targettransaction'] = this.transactionEvent;
}
sessionData[this.ontology.SessionStatus] = 'Initial';

// Clear out previous transaction state to ensure clean transitions
delete sessionData[this.ontology.ActivityInfo];
delete sessionData[this.ontology.ServiceResponseInformation];
delete sessionData[this.ontology.SessionWorkflowReturnLink];

Clearing out these keys prevents the task view from flashing stale content from previous runs. The session data is saved to Firestore via UpdateSessionDataService, and the workflow is started by hitting the orchestrator proxy at /api/orchestration/start.

2. Dynamic Task Rendering & Suspension

Once the workflow begins, the user is navigated to workflow-task.ts.

Ontology UI Rendering

The component queries the Firestore session document. When the workflow pauses for input, it writes an activityInfo object containing a dataset:catalogtype. The component requests the UI structural layout from OntologyService.getUITemplate(catalogType), which resolves recursively to inject forms dynamically via app-dynamic-primitive.

Submitting and Resuming

When the user enters data and submits, the component updates the Firestore document with the new activity data and changes the session status to 'Processing'. It then calls the orchestrator proxy endpoint /api/orchestration/resume/:executionId, passing the callbackUrl. This resumes the suspended GCP sub-workflow execution.

3. Zero-Latency & Pre-fetching Optimizations

In a naive workflow, moving to the next sequence step requires the user to wait for the backend to execute, write to Firestore, and update the UI. To deliver a premium user experience, several optimizations were implemented:

A. Silent Background Polling

Immediately upon calling the resume endpoint, the component kicks off startSilentBackgroundPoll(). This runs a background loop that reads the session data from Firestore every 1 second without blocking the UI or showing a loading spinner.

If the background poll finds that the parent workflow has already generated the next task (i.e. status is 'UserInput' and a new callbackUrl is set), it pre-fetches the entire payload and caches it in nextSessionData.

B. Instant Step Transitions

When the user clicks the "Continue to Next Task" button, continueSequenceOrReturn() checks if nextSessionData is populated: 

if (this.nextSessionData) {
  this.loading = true;
  this.activityTemplateStruct = undefined; // Avoid rendering stale layout
  this.activityData = null;
  this.successMessage = '';
  this.sessionData = this.nextSessionData;
  this.nextSessionData = null;
  this.cdr.detectChanges();
  this.processWorkflowState();
  return;
}

If the next task was pre-fetched during the time the user spent reading the success banner, the interface updates instantly with zero user-visible delay.

C. Zero-Latency Sequence Completion

When the final sub-transaction completes, we know there are no further prerequisites. Rather than polling Firestore to wait for the parent workflow to write 'Complete' (which takes 1-3 seconds and previously forced multiple retries), we determine this instantly in the frontend: 

get isLastTransactionInSequence(): boolean {
  if (!this.sessionData) return false;
  const workflow = this.sessionData['dataset:sessionworkflow'];
  const currentTx = this.sessionData['dataset:transaction'];
  const targetTx = this.sessionData['dataset:targettransaction'];
  return workflow === 'transactionsequence' && currentTx === targetTx;
}

If isLastTransactionInSequence is true, the button text instantly changes to "Return to Transactions". Clicking it navigates the user back immediately, eliminating all completion latency.
