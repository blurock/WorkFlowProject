Workflow & Backend Layer

Deep dive into the Google Cloud Workflows orchestrating transaction sequences and database updates.

Overview

The backend orchestration of transaction sequences is defined in transactionsequence.yaml and executed within Google Cloud Workflows. It coordinates Spring Boot microservices hosted on Cloud Run and handles nested sub-workflow triggers.

1. Parameters and Initialization

The workflow receives a single input containing the SessionData: 

main:
  params: [input]
  steps:
    - init:
        assign:
          - session_data: ${input.SessionData}
          - uid: ${session_data["dataset:authorizationuid"]}
          - session_id: ${session_data["dataset:sessionId"]}
          - transaction_event: ${session_data["dataset:transaction"]}
          - uniquegenericname: ${session_data["dataset:uniquegenericname"]}

2. Dependency Calculation

Ordered List of Prerequisites

The step get_prerequisites fires an HTTP POST request to the DatasetBackgroundServices microservice, requesting the service "OrderedListOfPrerequisites": 

    - get_prerequisites:
        call: http.post
        args:
          url: "https://dataset-background-services-315685320181.europe-west1.run.app/service"
          auth:
            type: OIDC
          body:
            uid: ${uid}
            service: "OrderedListOfPrerequisites"
            "prov:activity": ${transaction_event}
            "dataset:uniquegenericname": ${uniquegenericname}
        result: prereq_response

This retrieves the complete list of required transaction classes. The workflow appends the final target transaction event to this list, forming the full_list of events that must be verified and executed.

3. Prerequisite Checking & Sub-workflow Looping

The workflow loops over each event in full_list. For each event:

A. Existence Check

The workflow calls the "FindDatasetTransaction" service to determine if the transaction instance for the current event already exists in Firestore: 

            - check_prerequisite_exists:
                call: http.post
                args:
                  url: "https://dataset-background-services-315685320181.europe-west1.run.app/service"
                  auth:
                    type: OIDC
                  body:
                    uid: ${uid}
                    service: "FindDatasetTransaction"
                    "prov:activity": ${current_event}
                    "dataset:booleanonlyone": false
                    "dataset:activityinfo":
                      "dataset:catalogobjectmaintainer": ${uid}
                      "dataset:uniquegenericname": ${uniquegenericname}
                      "dataset:objecttype": ${current_event}
                result: find_response

B. Sub-workflow Execution (Conditional)

If dataset:servicesuccessful is not "true", the transaction is missing. The parent workflow launches the child workflow "single-transaction-workflow": 

                      - execute_subworkflow:
                          call: googleapis.workflowexecutions.v1.projects.locations.workflows.executions.run
                          args:
                            workflow_id: "single-transaction-workflow"
                            project_id: ${sys.get_env("GOOGLE_CLOUD_PROJECT_ID")}
                            location: ${sys.get_env("GOOGLE_CLOUD_LOCATION")}
                            argument: ${subworkflow_args}
                          result: subworkflow_result

This child workflow registers callback URLs, saves state, and halts until user interaction resumes it.

C. Re-querying Session Data

After the child workflow resumes and successfully finishes its task, the parent workflow queries the updated session document using ReadSessionDataService and updates its local state variable session_data: 

                      - requery_session_data:
                          call: http.post
                          args:
                            url: "https://dataset-background-services-315685320181.europe-west1.run.app/service"
                            auth:
                              type: OIDC
                            body:
                              uid: ${uid}
                              "<http://purl.org/dc/elements/1.1/identifier>": "dataset:sessiondata"
                              "dataset:authorizationuid": ${uid}
                              service: "ReadSessionDataService"
                              "dataset:sessionId": ${session_id}
                          result: new_session_response

4. Resiliency & Type Safety

Type Error Mitigation

In Cloud Workflows, standard string() functions can crash if passed list structures instead of primitives (e.g., if a loop variable resolves to an array under specific branches). To handle logging safely, the workflow utilizes json.encode_to_string(): 

text: '${"parse_subworkflow_output completed for event: " + json.encode_to_string(current_event)}'

Pre-parsed Response Direct Mapping

The Cloud Workflows HTTP connector automatically pre-parses HTTP responses. Attempting to parse the nested result body field manually using json.decode() led to `KeyError` crashes. Reverting to direct assignment resolved this: 

- parse_subworkflow_output:
    assign:
      - run_output: ${subworkflow_result}
